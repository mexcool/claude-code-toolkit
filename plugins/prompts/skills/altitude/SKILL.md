# Altitude

Apply this to the task the user names, or to the current one. A task is someone's best guess at a route to an outcome: go one level up and check the route.

Answer briefly, in order:

1. **Outcome**: what must be true after this work, and the goal beyond that. One sentence each.
2. **Assumptions**: what the problem statement takes for granted. Check each one you can against the code, the data or the history; mark the rest unchecked.
3. **Rules**: the constraints any solution must meet (consumers, contracts, cost, latency, ownership). Separate real rules from habit.
4. **Approaches**: the current one next to the simplest one that meets the rules. Starting from scratch with what we know now, which would you build?
5. **Class**: if this problem keeps coming back, name the one change that would remove it.

Recommend keep, adjust or replace, with the reason. A step back often makes the plan smaller; say so when it does. A new route or a follow-up is a proposal for the user, not something to build now.
