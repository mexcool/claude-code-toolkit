Be more ambitious

Three ways to be more ambitious with a model without growing the change. Put the ambition into evidence and into questions for you. Keep the diff as small as the problem allows.

After Felix Rieseberg, How to be more ambitious (October 2026).

The three moves

Pick the one the task needs. Most tasks need one; few need all three. Each is also a command: type it after your request, or paste the prompt.

↑Altitude/altitude

Work one level up: the outcome the task is a guess at.

Reach for it when

The ticket prescribes the fix. You would call a meeting about it. The same kind of ticket keeps coming back.

Type this

Step back before you answer. What must be true after this, and what is the goal beyond that? Are the problem's assumptions right? What rules must any solution follow? Now judge this approach against the simplest one that meets them.

Looks like

"Fix this crash" becomes "keep the app crash-free". A step back often makes the plan smaller: an over-built pipeline redone with half the parts.

When a ticket is done, ask which class it belongs to, and whether one follow-up would remove the class.

↓Depth/deeper

Work the way the best engineer in the field would: from raw evidence, with real instruments.

Reach for it when

It has to be right, not only done. Someone calls a risk "accepted" or a case "impossible" without measuring it.

Type this

I want a deeper version of this, not a bigger one. Before you start: what is the rawest evidence (data, logs, a real run; not the schema or my summary)? What would the best engineer here run to check it? What, other than you or me, would show it's right? Then do exactly that.

Looks like

"Add a retry" starts with sorting the incident's failures from the logs. Result: the retry would have saved 0 of 10, so fix what actually failed.

Set a high bar for proof: all 90 days, not 3 examples.

↔Range/range

Borrow the methods of other fields the work touches.

Reach for it when

The work touches people, money, shared capacity, or numbers someone decides on.

Type this

Say what this does as a verb, not a noun. Which fields deal with that verb every day, and what is the one check each would run? Run those checks. Don't role-play the field.

Looks like

"Parallelize the reads" becomes "serve more requests from a shared, bounded pool without starving anyone". That is capacity planning, whose check is a load test on the real pool.

Use a field for its methods. "Review as an SRE" changes the tone; "replay 90 days and count the pages" changes the result.

Don't let it grade itself

A model's "looks good" is not evidence. Ask for a check that something else runs: a test, a query, a diff of outputs. Run it on main and on the branch, against the real dependency. A mock that skips the risky behaviour proves nothing about it.

For a second opinion, give a fresh agent the work, not your conclusion. /deeper includes this check.

Type this

Don't grade your own work. Name the command or query whose output would convince a skeptic, run it on main and on the branch through the real dependency, and show me both outputs.

What deep looks like

Shallow work changes the words. Deep work changes the method.

TaskShallowDeep
Wrong numbersRead the SQL, spot the fan-out, add DISTINCT.Reproduce one bad key from the raw tables. Fix the grain. Diff old vs new per key over the same window. Count the days and the downstream readers affected.
Slow queryChange the sort key on a hunch: "should be faster".Take the real query from the query log (rows read, memory). EXPLAIN it. Compare before and after on the same data and settings, several runs each.
Shared poolMock-transport tests; "starvation is an accepted limit".Concurrent callers on the real pool, main vs branch. One run showed 200 on main and 502 on the branch.
Error mappingUnit-test the classifier with a hand-built error.Send a real 429 through the production retry setting. The wrapper hid the status the classifier needed.
Schema changeRead the schema.Query the historical rows: null rates, old shapes, values the schema allows but nobody expected.
Flaky jobWrap it in a retry.Sort the failures from the logs by shape. Check the write is idempotent before retrying it. Test the most frequent failure, not the easiest one.

Borrow a check

Find the verb, then borrow the method of the field that lives with it.

If the work…Borrow this check
pages someone at nightReplay history and count how often it would fire. Test the route end to end.
shares a limited resourceWorst-case concurrency against the real limit. A load test.
makes numbers people decide onReconcile with an independent source. The parts sum to the whole. Diff per key.
ranks or scores peopleSmall-sample noise and survivorship. How would someone game it?
changes a contract others readList every consumer, then check each one.
costs money per runCost per run, before and after.
runs unattendedRerun it, and kill it halfway. What happens?
tells a user somethingOne row per failure: what they see, what they do next.

Traps

Where asking for more goes wrong.

  • Bigger instead of deeperMore features, more abstractions, more checks shipped to production. Depth belongs in the proof, not in the product.
  • Argued risk"Edge case" and "accepted limit" with no measurement behind them. Ask what run shows it.
  • Role-playA persona changes the transcript, not the outcome. Ask for the field's method.
  • No accessAn agent that can't reach the logs or the data reasons around them. Fix the access once, not on every ticket.
